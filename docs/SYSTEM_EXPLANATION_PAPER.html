1. Introduction & Operational Context

JM Maker Sportswear is a customized jersey manufacturing and sublimation printing enterprise located in Cabuyao, Laguna, serving individual clients, sports teams, schools, and corporate groups. Prior to this system, daily operations relied on handwritten logbooks to record customized order specifications, compute prices and partial balances, verify GCash transfers, update finished-goods stock, track production progress, and summarize sales.

Based on the capstone proposal and 25-question client interview transcript (Appendix A), the developed web application centralizes Point of Sale (POS), Custom Order Tracking, Finished Goods Inventory, Tokenized Payment Verification, Staff Monitoring with Role-Based Access Control (RBAC), Automated Notifications, Sales Analytics, and Database Backup & Recovery into a unified platform.

3. System Architecture & User Roles (RBAC)

The application consists of three Vite-bundled web pages: index.html (Sign-In, Account Creation & Recovery), dashboard.html (9-module authenticated workspace), and buyer.html (token-gated zero-login payment proof upload portal). It runs natively on Supabase PostgreSQL + Supabase Auth + Realtime when configured via .env.local, and automatically falls back to browser localStorage with zero preloaded demo records for offline demonstrations.

Role Permitted Scope Enforced Security Restrictions
Owner / Manager (owner_manager) Full access to all 9 modules, staff directory & RBAC administration, payment verification, and JSON backup/restore/reset utilities. Cannot modify or delete records in audit_logs (immutable append-only).
Supervisor (supervisor) Dashboard Overview, Notifications, Staff Monitoring (view directory, assign/update tasks, inspect audit trail), plus assigned RBAC modules. Cannot create/delete staff profiles, modify RBAC permissions, restore backups, or reset store data.
Shop Staff (staff) Dashboard Overview, Notifications, and only the module permissions checked by the Owner (POS, Orders, Inventory, Payments, Reports). Unauthorized sidebar items hidden; navigation blocked by canAccessPage(); Inactive accounts blocked at sign-in.
Customer / Buyer (anon token-scoped) Single-order receipt submission & status lookup via opaque buyer.html?token=jm_... link. Zero direct PostgreSQL table privileges; all access mediated by SECURITY DEFINER RPCs.

4. Core System & Staff Monitoring Workflows

4.1 Custom Order, Payment Verification & 4-Step Fulfillment Flow

[1. Custom Orders & POS] Capture customer name, contact info, jersey package, colorway, printing, template, sizes (XS–XXL+ +₱50), & ₱ discount │ ├──> [Payment Link Generated] Opaque URL (buyer.html?token=jm_...) sent to customer │ └──> Buyer uploads GCash/Bank proof + ref code (no login) │ └──> Owner Reviews: Reject (re-opens link) OR Approve (atomic order credit + sales_logbook + audit) │ └──> [4-Step Guided Fulfillment] Step 1: Review Order (Order Received) ──> Step 2: Prepare Order (Production checklist: Design + All Pieces) ──> Stages Completed Custom Stock ──> Step 3: Check Order (QC checklist: Qty + Print/Stitching) ──> Fires "Ready for Release" Alert ──> Step 4: Complete Fulfillment (Blocked unless Balance == ₱0) ──> Released & Clears Staging Stock

4.2 Staff Monitoring & Immutable Accountability Flow (Objective 4)

[Owner/Manager] Registers Staff Profile (Code, Position, Shift, Availability) + Assigns 5 RBAC Module Permissions │ ├──> [Authentication Audit] Staff signs in/out ──> Updates lastLoginAt & logs immutable 'login'/'logout' event ├──> [Operational Tasks] Assign Production / QC / Inventory / Release Task linked to Order or SKU │ └──> Pending ──> In Progress ──> Completed (stamps completedAt + logs 'task_update' + notifies owner) └──> [Activity Accountability] Every Order Update, Price Edit, Stock Adjustment, Payment & Backup records: (Timestamp, Actor Name, Actor Role, Event Type, Module, Action Description) in Append-Only audit_logs └──> Live KPIs (v_staff_performance_summary) + Searchable Trail + Printable Staff Monitoring Report

5. Normalized Supabase PostgreSQL Database Design

Implemented across four chronological, non-destructive SQL migrations (202611260001 through 202611280004) totaling 13 normalized tables, 2 security-invoker views (v_monthly_sales_summary, v_staff_performance_summary), and 6 transactional RPCs:

  • Core Store & Staff Tables: owner_profiles (1:1 with auth.users), staff_members (1:N with 5 RBAC flags), staff_tasks (1:N from staff, 0..1:N to orders/inventory).
  • POS & Fulfillment Tables: custom_orders (with client_contact, discount_amount, assigned_staff_id), order_size_items (1:N normalized sizes), order_fulfillment_checklists (1:1 step flags), inventory_items (finished goods + 0..1:0..1 pickup staging).
  • Payments, Sales & Governance Tables: payment_accounts, payment_verification_links, payment_proof_submissions (1:N retries per link, partial unique active ref numbers), sales_logbook (unique credit per approved proof), notifications, and append-only audit_logs.

8. Scope Limitations & Production Verdict

  • Manual GCash / Bank Verification Only: No live GCash API integration; reference numbers and proof screenshots are manually verified by the owner (Interview Q9).
  • Finished Goods Scope Only: Tracks ready-made stock and completed custom orders; excludes raw materials such as fabric rolls, thread, and ink (Interview Q12, Q24).
  • Digital Tracking Only: Monitors production stages and checklists without automating physical printing or sewing equipment; report accuracy depends on user data entry.
  • Cloud Multi-Device Staff Auth Note: Local/workstation staff logins work immediately via Staff Directory credentials; multi-device Supabase cloud staff sessions can be bound to staff_members.auth_user_id when provisioned in Supabase Auth.
